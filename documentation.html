1. Project Overview

The Military Asset Management System (MAMS) is a mission-critical enterprise defence solution engineered to track, control, and audit the lifecycle of strategic military equipment (including armoured vehicles, armaments, 7.62mm/155mm munitions, and vital rations) across distributed operational sectors.

1.1 Core Objectives

  • Perpetual Balance Ledger: Real-time tracking of Opening Balances, Net Movements, and Closing Balances adhering to the formula: Closing Balance = Opening Balance + (Purchases + Transfers In - Transfers Out) - (Assignments + Expenditures)
  • Inter-Base Custody Tracking: Multi-state workflow governance (Pending → Approved → In-Transit → Completed / Cancelled) ensuring two-party custody confirmation between transferring and receiving bases.
  • Personnel Accountability: Rigorous tracking of individual weaponry and equipment assignments with serial numbers, personnel identifiers, and return timestamps.
  • Tamper-Resistant Audit Trail: Complete transactional logging of every mutation across the system for parliamentary and defence oversight.

1.2 Assumptions & System Boundaries

  • Operational Boundaries: Bases operate within isolated inventory scopes. A Base Commander cannot modify assets or approve transfers outside their assigned military sector.
  • Asset Atomic Integrity: Munitions and fuel are tracked in discrete metric units (rounds, litres). Stock balances can never drop below zero; atomic database transactions guarantee inventory consistency.
  • Network Resiliency: The architecture supports low-bandwidth and high-latency military networks with sub-second REST response times and client-side token caching.

2. Tech Stack & Architecture Justification

The system utilizes a modern, typed, multi-tier decoupled architecture designed for high availability, zero cold-starts, and rigid security boundaries.

Layer Technology Chosen Architectural Justification
Frontend React 18, Vite, TypeScript, Tailwind CSS, Lucide Icons, Zustand Fast HMR, compile-time type safety, lightweight bundle (~470 KB), responsive mobile-first UI for forward tactical terminals, atomic store management.
Backend Node.js, Express.js, TypeScript, Zod, Pino Logger High-throughput asynchronous I/O, declarative schema validation with Zod, structured high-speed JSON auditing with Pino.
Database & ORM PostgreSQL 16 (Neon Serverless), Prisma ORM Why SQL/PostgreSQL over NoSQL: Military asset accounting requires ACID transactions, foreign key constraints (cascading approvals, stock locks), strict uniqueness guarantees, and complex aggregations (Opening/Closing balance calculations). NoSQL lacks deterministic cross-document transactional locks needed for physical munitions accountability.
Cloud Infrastructure Vercel (Frontend Edge CDN) + Railway (Backend Microservice) + Neon (Cloud Pooler) Global edge distribution with zero-downtime CI/CD deployment, automated SSL/TLS termination, and serverless pooled database connections.

3. Data Models & Database Schema

The database schema is structured around 11 normalized relational entities enforced by strict foreign key relationships, check constraints, and composite unique indexes.

Table Name Primary Keys & Relations Purpose & Critical Attributes
users id (UUID PK), base_id (FK → bases) Stores credentials, pre-hashed bcrypt passwords, assigned operational roles (ADMIN, BASE_COMMANDER, LOGISTICS_OFFICER).
bases id (UUID PK) Military installations (e.g., Camp North, Camp South, Central Depot, Airbase East).
equipment_types id (UUID PK) Master equipment catalog with standardized categories (WEAPON, VEHICLE, AMMUNITION, SUPPLY).
stock_balances id (UUID PK), UNIQUE(base_id, equipment_type_id) Real-time atomic ledger of physical stock on hand per base and equipment item.
purchases id (UUID PK), recorded_by_id (FK → users) Inward procurement transactions with unit price, supplier name, and purchase timestamps.
transfers from_base_id (FK), to_base_id (FK), approved_by_id (FK) Inter-base asset relocations with state tracking (PENDING, APPROVED, IN_TRANSIT, COMPLETED).
transfer_events transfer_id (FK → transfers) Immutable historical log tracking who changed the transfer state and why.
assignments base_id (FK), assigned_by_id (FK) Armament issuance to military personnel (Army ID, Name, Return date, Status).
expenditures base_id (FK), expended_by_id (FK) Consumed assets (training rounds, diesel fuel, live-fire exercise munitions).
audit_logs id (UUID PK), user_id (FK) Immutable transactional ledger recording user actions, IP, user-agent, route, and payloads.
refresh_tokens user_id (FK → users) Secure cryptographic rotation tokens for 7-day extended session management.

4. Role-Based Access Control (RBAC)

Security is enforced through a two-stage perimeter: cryptographic JSON Web Token (JWT) verification followed by role and base-level permission middleware.

Role Scope of Authority Permitted Operations Restricted Operations
ADMIN Nationwide (All Bases) Full CRUD access to all bases, stock adjustments, purchase authorization, nationwide audits, user management. None (HQ Master Clearance).
BASE_COMMANDER Assigned Base Only Approve/reject transfers involving their base, manage local assignments & expenditures, view local ledger. Cannot view or modify other bases' inventory; cannot initiate centralized depot purchases.
LOGISTICS_OFFICER Ordnance & Procurement Record incoming purchases, initiate transfer requests between bases, view catalog metrics. Cannot approve transfers; cannot assign weapons to personnel; cannot access administrative audits.
Security Enforcement Mechanism
All backend API routes pass through authenticateToken, which validates the RSA/HMAC signature and extracts user metadata. Specific routes then invoke authorize(Role.ADMIN, Role.BASE_COMMANDER). For base-level operations, the controller automatically injects req.user.baseId for non-admins, preventing cross-tenant data leaks.

5. API Logging & Audit Ledger

To comply with military transparency mandates, all state-mutating requests (POST, PUT, PATCH, DELETE) automatically trigger an audit record captured by the centralized audit interceptor.

  • Actor Attribution: Exact User ID, User Role, and originating Base ID.
  • Network Metadata: Remote IPv4/IPv6 address and User-Agent signature.
  • Payload Delta: Stores state snapshots in payload_before and payload_after JSONB columns.
  • Non-Blocking Async Dispatch: Audit writes are dispatched asynchronously via Prisma without hindering HTTP request latency.

9. CI/CD Pipeline & DevOps Architecture

To adhere to strict defence software lifecycle standards, MAMS implements an automated, multi-stage Continuous Integration and Continuous Deployment (CI/CD) pipeline configured via GitHub Actions (.github/workflows/ci-cd.yml) combined with edge-native deployment hooks.

9.1 Pipeline Workflow Stages

Stage Environment & Tooling Execution Steps & Quality Checks
1. Backend CI Ubuntu 22.04, Node.js 20, npm cache
  • Checks out codebase and restores cached npm dependencies.
  • Executes npx prisma generate to compile type-safe database access layer.
  • Enforces zero-tolerance static analysis with npx tsc --noEmit.
  • Executes production build (npm run build) to produce clean Node artifacts.
2. Frontend CI Ubuntu 22.04, Node.js 20, Vite Build Engine
  • Restores client dependencies via deterministic npm ci.
  • Executes TypeScript compiler across client modules (tsc -b).
  • Runs Vite compiler (vite build), checking bundle optimization.
  • Validates output artifact integrity (verifies dist/index.html existence).
3. Continuous Deployment (CD) Vercel Edge Network + Railway Container Engine
  • Frontend: Automatically built and deployed to Vercel global edge CDN upon passing main branch checks.
  • Backend: Containerized and rolled out to Railway with zero-downtime health switching.
4. Automated Health Probe Automated cURL Smoke Test
  • Pings live backend health endpoint (GET /health) and asserts HTTP 200.
  • Pings live Vercel frontend URL and verifies edge status code 200.

9.2 Zero-Secret Security Paradigm

Rather than storing long-lived personal access tokens or high-risk API keys within GitHub repository secrets, the pipeline utilizes native Git OAuth application webhooks integrated directly between GitHub, Vercel, and Railway. This design guarantees:

  • Reduced Attack Surface: Zero cloud deployment credentials exposed in repository settings or CI runner memory.
  • Automated Rollback & Audit: Any build or type failure in Stage 1 or Stage 2 prevents deployment rollout, preserving production stability.
  • Full Traceability: Every deployment corresponds immutably to a verified Git commit SHA and signed audit record.
